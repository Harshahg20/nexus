### Architecture

The agent will have **two** tool types:

**Tool 1: `nexus_analyst`** (type: `cortex_analyst_text_to_sql`)
- Backed by `NEXUS_DB.SEMANTIC.NEXUS_SUPPLY_CHAIN`
- Handles all **baseline analytics**: supplier lookups, part dependencies, inventory, orders, BOM, shipments
- Governed by the semantic view's custom instructions, VQRs, and entity definitions

**Tools 2-5: Scenario engine tools** (type: `generic`)
- Each backed by a SQL UDF in `NEXUS_DB.TOOLS` schema (new)
- UDFs execute SELECT against the deterministic scenario views
- Returns VARIANT (JSON) so the Agent can reason over structured results

| Tool Name | UDF | Purpose | Input | Backed by |
|---|---|---|---|---|
| `run_supplier_failure` | `TOOLS.RUN_SUPPLIER_FAILURE_SCENARIO` | Run supplier failure scenario | `supplier_id`, `duration_days`, `capacity_reduction_pct` | V_SUPPLIER_FAILURE_IMPACT + V_SUPPLIER_FAILURE_CHAIN |
| `compare_mitigations` | `TOOLS.COMPARE_MITIGATIONS` | Compare mitigation strategies | (none — reads active params) | V_MITIGATION_COMPARISON |
| `run_port_disruption` | `TOOLS.RUN_PORT_DISRUPTION_SCENARIO` | Run port disruption scenario | `port_id`, `duration_days`, `disruption_pct` | V_PORT_DISRUPTION_IMPACT + V_PORT_DISRUPTION_CHAIN |
| `get_freight_shock` | `TOOLS.GET_FREIGHT_SHOCK_SUMMARY` | Freight cost shock analysis | (none — reads active params) | V_FREIGHT_SHOCK_SUMMARY + V_FREIGHT_SHOCK_CHAIN |

**Why UDFs, not stored procedures?**
- The scenario views are parameterized via `V_ACTIVE_*_PARAMETERS` views (currently hardcoded)
- For MVP: UDFs read the current active parameters and query the scenario views, returning JSON
- The UDFs are read-only (SELECT only) — no autonomous actions
- Future: procedures could UPDATE the parameter views for dynamic what-if

**Tool mapping to original contract:**
1. `resolve_entity` → handled by `nexus_analyst` (Cortex Analyst resolves names via semantic view)
2. `run_governed_metric` → handled by `nexus_analyst` (metric catalog in semantic view)
3. `run_scenario` → `run_supplier_failure` / `run_port_disruption` tools
4. `trace_dependency` → `run_supplier_failure` returns the chain; `nexus_analyst` handles baseline BOM tracing
5. `compare_mitigations` → `compare_mitigations` tool

### Implementation Steps

**Step 1: Create TOOLS schema**
```sql
CREATE SCHEMA IF NOT EXISTS NEXUS_DB.TOOLS;
```

**Step 2: Create 4 SQL UDFs** (read-only, return VARIANT)
- `RUN_SUPPLIER_FAILURE_SCENARIO()` — returns JSON with impact summary + top chain rows
- `COMPARE_MITIGATIONS()` — returns JSON array of mitigation strategies
- `RUN_PORT_DISRUPTION_SCENARIO()` — returns JSON with port impact + chain
- `GET_FREIGHT_SHOCK_SUMMARY()` — returns JSON with freight shock analysis

Each UDF selects from existing scenario views and packages results as OBJECT_CONSTRUCT / ARRAY_AGG.

**Step 3: Create Agent** in `NEXUS_DB.PUBLIC`
```sql
CREATE OR REPLACE AGENT NEXUS_DB.PUBLIC.NEXUS_SUPPLY_CHAIN_AGENT
  COMMENT = 'NEXUS Supply Chain Resilience Agent'
  PROFILE = '{"display_name": "NEXUS Supply Chain", "color": "blue"}'
  FROM SPECIFICATION $$ ... $$;
```

**Agent instructions will include:**
- Response: supply-chain domain context, "modeled" disclaimers for scenarios
- Orchestration: routing rules (baseline → analyst, scenario → tools, mitigation → compare tool)
- Sample questions: 4 canonical user journeys

**Step 4: Create deployment SQL file**
- `snowflake/014_nexus_agent.sql` — contains all of the above in order

### Test Plan

   ```sql

     'NEXUS_DB.PUBLIC.NEXUS_SUPPLY_CHAIN_AGENT',
     'Which suppliers provide critical parts?'
   ```

   ```sql
   SELECT SNOWFLAKE.CORTEX.DATA_AGENT_RUN(
   ```

   ```sql
   SELECT SNOWFLAKE.CORTEX.DATA_AGENT_RUN(
     'NEXUS_DB.PUBLIC.NEXUS_SUPPLY_CHAIN_AGENT',
     'What products depend on PART-104?'
   ```

4. **Mitigation test:**
   ```sql
   SELECT SNOWFLAKE.CORTEX.DATA_AGENT_RUN(
     'NEXUS_DB.PUBLIC.NEXUS_SUPPLY_CHAIN_AGENT',
     'What can we do to reduce the impact?'
   );
   ```

5. **Verify:** each response uses the correct tool (analyst vs scenario), scenario outputs are labeled as "modeled", no arbitrary SQL execution occurs.
